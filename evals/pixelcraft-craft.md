# pixelcraft-craft evaluation cases

## Case 1 — visual language

**Prompt**

> Define the visual language for a archival photography product.

**Expected behaviors**

- Selects or applies `pixelcraft-craft` behavior when the prompt matches its trigger.
- uses material/typography/color/motion with clear rationale.
- includes a rendered inventory plan for font faces/sizes, palette count by role, whitespace/width geometry, motion signals, and reduced-motion fallbacks without treating calibration ranges as targets.
- specifies palette construction, type pairing roles, motion budget, fallback, and reduced-motion path.
- assigns a mode-appropriate visual-complexity budget instead of equating novelty with clutter or sparse output with quality.
- avoids derivative interface tropes.
- Preserves truthful content, necessary states, accessibility, security/privacy constraints, and honest evidence labels.

**Failure signals**

- purple gradient/glassmorphism default.
- no editorial hierarchy.
- decorative noise.

**With-vs-without comparison criteria**

| Dimension | Without skill baseline | With skill target |
|---|---|---|
| Trigger/routing | Implements directly with generic assumptions | Recognizes the domain and applies the matching skill/reference |
| Constraint fidelity | Relies on common defaults or stale APIs | Uses the exact surface constraints, state model, and platform idioms in the expected behaviors |
| Verification | Reports code/text output only | Provides appropriate rendered/static/model evidence and labels unavailable checks |

## Case 2 — detail pass

**Prompt**

> Polish a sparse markdown editor interface.

**Expected behaviors**

- Selects or applies `pixelcraft-craft` behavior when the prompt matches its trigger.

- Documents platform constraints, missing states, and verification tradeoffs explicitly.
- Preserves truthful content, necessary states, accessibility, security/privacy constraints, and honest evidence labels.
