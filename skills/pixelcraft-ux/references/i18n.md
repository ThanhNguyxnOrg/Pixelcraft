# International UX

Evidence: Unicode locale data, W3C internationalization guidance, logical layout behavior, and cross-cultural variation. Treat every writing system as a first-class constraint. Do not center one language or transliterated ASCII as the default human reality.

## Script and text-engine requirements

| Script family | Required behavior |
|---|---|
| Latin with diacritics | Preserve base letters, combining marks, normalization, and mark positioning. Vietnamese and Polish are examples only—not special cases. Test stacked tone/underdotted marks, uppercase forms, casing, search normalization, and font clipping. Do not strip accents for validation or storage. |
| Cyrillic/Greek | Preserve native alphabets without treating them as Latin lookalikes. Test casing/locales, sorting, glyph coverage, italic availability, and stress marks. Greek uses context-sensitive final sigma; let the text engine handle it rather than manipulating letters manually. |
| Arabic/Hebrew/Persian | Support right-to-left layout, contextual shaping, ligatures, joining, diacritics where used, native/European digits as locale-appropriate, and mixed-direction runs. Never split or reverse strings by code point. Persian digits/letterforms and Arabic-script language variation are not interchangeable automatically. |
| CJK | Respect locale-specific line breaking/prohibition rules, punctuation compression, ruby/furigana needs where relevant, and no-space scan behavior. Do not synthesize italics by skewing CJK glyphs; use weight/color/semantic emphasis instead. Vertical writing can be culturally appropriate but changes line progression, punctuation, numerals, ruby, scrolling, and text metrics—test it deliberately rather than rotating horizontal text. |
| Thai/Lao/Khmer | These scripts do not use spaces as ordinary word separators. Use dictionary/locale-aware segmentation for search, selection, wrapping, and measurement. Browser/runtime behavior differs by font/platform. |
| Indic scripts | Correct rendering depends on complex shaping: reordering, conjuncts, matras, ligatures, clusters, and script-specific font tables. Never truncate/split inside a grapheme/orthographic cluster and never shape manually in application code. |
| Emoji/ZWJ sequences | Emoji can be multi-code-point graphemes using ZWJ, skin-tone modifiers, flags/regional indicators, variation selectors, and keycap sequences. JavaScript `.length` counts UTF-16 code units and is not a user-perceived character count. |

## Bidi isolation and logical layout

Use `dir="auto"` or explicit direction on user-generated mixed-direction text and isolate inline fragments:

```html
<span dir="auto">اسم المستخدم</span>
<bdi>@user</bdi>
```

CSS form: `unicode-bidi: isolate` / `plaintext` where appropriate. Isolate filenames, handles, URLs, error excerpts, brand names, and user-generated strings inserted into opposite-direction prose. Keep punctuation attached to the correct semantic fragment.

Use logical properties (`margin-inline-start`, `padding-inline`, `inset-block`, `border-start-end-radius`) rather than physical left/right when meaning follows reading direction. Mirror navigation/progression/layout only when direction is semantic. Do **not** blindly mirror numerals, charts' chronological direction, clocks, playback/media symbols, mathematical notation, playback progress direction, asymmetric product screenshots, or culturally directional iconography.

## Segmentation and grapheme counting

Use `Intl.Segmenter` where available:

```js
const segmenter = new Intl.Segmenter('th', { granularity: 'word' });
const words = [...segmenter.segment('ภาษาไทย')].map((part) => part.segment);

const graphemes = new Intl.Segmenter('en', { granularity: 'grapheme' });
const count = [...graphemes.segment('👨‍👩‍👧‍👦')].length; // 1
```

Rules:

- use `granularity: 'word'` for Thai/Lao/Khmer word segmentation where supported; provide fallback behavior because segmentation quality/availability varies;
- use `granularity: 'grapheme'` for maxlength counters, caret movement, truncation, avatars/initials, and deletion behavior;
- never count UTF-16 units or bytes as user-visible characters;
- test surrogate pairs, combining marks, regional-indicator flags, family/profession emoji, variation selectors, and skin tones;
- search indexing/tokenization may need a different locale pipeline from display truncation.

## Font fallback stacks

Fallback must be explicit per script and font role. Examples are starting points, not universal mandates:

```css
font-family:
  "Inter", "Noto Sans", system-ui, sans-serif; /* Latin/Cyrillic/Greek baseline */

font-family:
  "Noto Sans Arabic", "Noto Naskh Arabic", "Segoe UI", sans-serif; /* Arabic/Persian */

font-family:
  "Noto Sans Hebrew", "Arial Hebrew", sans-serif; /* Hebrew */

font-family:
  "Noto Sans CJK SC", "PingFang SC", "Microsoft YaHei",
  "Noto Sans CJK JP", "Hiragino Sans", "Yu Gothic",
  "Noto Sans CJK KR", "Malgun Gothic", sans-serif; /* CJK examples */

font-family:
  "Noto Sans Thai", "Leelawadee UI",
  "Noto Sans Khmer", "Khmer UI",
  "Noto Sans Lao", "Lao UI", sans-serif; /* mainland SE Asian examples */

font-family:
  "Noto Sans Devanagari", "Noto Sans Bengali", "Noto Sans Tamil",
  "Noto Sans Telugu", "Noto Sans Kannada", "Noto Sans Malayalam", sans-serif;
```

Add emoji fallback such as platform emoji fonts where the product expects emoji rendering. Do not list fonts you do not test or ship/license. Metrics differ by script: line height, ascender/descender clipping, mark attachment, baseline alignment, underline/strike position, and weight synthesis must be inspected. Disable fake/oblique synthesis for CJK where possible (`font-synthesis` controls on web) and avoid synthetic bold when the font lacks proper weight.

## Expansion, contraction, and layout budgets

A 30–40% expansion budget is a useful baseline for dense Latin-first UI, not a universal guarantee. Short labels can expand far more; CJK can contract visually while line count increases because fewer characters fit per line. Design rules:

- use wrapping/flexibility before truncation;
- reserve no fixed width for critical labels without an overflow rule;
- test both expansion and contraction;
- preserve minimum hit targets after translation;
- avoid vertically centered single-line assumptions;
- never use ellipsis in legal/safety/destructive confirmation text without an inspectable full-text path;
- measure using real translations plus pseudo-localization, not guessed length multiplication alone.

## ICU plural, gender, and message structure

Use complete locale-aware messages; never concatenate grammar around variables. ICU MessageFormat supports plural/select/selectordinal and nested formatting. Example shape:

```text
{gender, select,
  female {She}
  male {He}
  other {They}
} updated {count, plural,
  one {# file}
  other {# files}
}
```

Correct behavior depends on locale plural categories: languages may use zero/one/two/few/many/other and different semantics. Gender is message/context dependent; do not infer it from names. Preserve placeholders, formatting types, escaping, and translator context. Do not reuse one key in multiple grammatical contexts merely because the English source matches.

## Locale formatting with platform APIs

Use `Intl`/CLDR-backed APIs rather than hand formatting:

- `Intl.DateTimeFormat` for dates/times/calendars/time zones;
- `Intl.NumberFormat` for decimal/currency/percent/unit notation;
- `Intl.RelativeTimeFormat` for localized relative time;
- `Intl.ListFormat` for conjunction/disjunction lists;
- `Intl.DisplayNames` for language/region/script/currency names;
- `Intl.Collator` for sorting/search matching with numeric/case/accent sensitivity options.

Do not hard-code digit grouping, decimal separators, month/day order, 12/24-hour clocks, week start, currency symbol placement, negative signs, capitalization, or list punctuation. Persist exact timestamps/values separately from localized display strings.

## Platform notes

| Platform | Notes |
|---|---|
| Web | `dir`, `lang`, logical CSS, `unicode-bidi`, `Intl`, font `unicode-range`, line breaking/hyphenation vary by browser/lang. Verify actual shaping in target browsers and test `input` behavior during IME composition. |
| iOS/macOS | use localized strings dictionaries/plural rules, `NSLocale`/formatters, correct semantic content/input direction; test Dynamic Type, line-height clipping, keyboard/IME composition, and localized collation. |
| Android | use resources/plurals/`strings.xml`, locale-aware formatters, `textDirection`, font fallback, and `Layout` measurement; test pseudo-locales, RTL layout direction, IME composition, and per-app language preferences. |
| Flutter | use ICU-backed localization/message package plus `Directionality`, locale-aware text measurement/rendering, correct font fallback, and integration tests for RTL/CJK/emoji. Do not rely on pixel count or `String.length`. |
| Qt/QML | use `qsTr`/translation catalogs, plural-aware overloads, locale-aware formatting, correct `LayoutMirroring`/input method behavior, and font fallback validation. Test desktop/mobile input-method editors. |
| Terminal/TUI | width calculation is ambiguous: Unicode width, combining marks, East Asian wide/fullwidth, emoji presentation, and terminal emulator support differ. Do not assume one code point equals one cell; test truecolor/NO_COLOR/mono fallback and avoid relying on complex shaping that terminals may not perform. |

## Testing with pseudo-localization

Pseudo-localization expands text, adds visible boundaries/accents, and can simulate RTL or placeholder corruption. Use it to detect hard-coded strings, concatenation, clipping, missing locale fallback, encoding errors, and layout fragility. It is not a substitute for real translation or native-speaker review.

Minimum fixture matrix for international products:

1. Latin text with combining/stacked diacritics and long compound words;
2. Cyrillic and Greek native text;
3. Arabic plus Hebrew/Persian mixed-direction examples;
4. Chinese/Japanese/Korean text and IME input;
5. Thai/Lao/Khmer segmentation examples;
6. at least one relevant Indic script;
7. emoji/ZWJ/flag/keycap sequences;
8. plural categories from multiple language families;
9. locale-formatted dates/numbers/currency/lists;
10. pseudo-localized expansion plus real RTL layout.

Label unavailable review/rendering evidence `not-checked`; passing English-only screenshots is not international verification.

## Message authoring rules

Write translatable messages as complete semantic units:

- never concatenate sentence fragments around variables because word order, case agreement, gender, number, and prepositions change by language;
- pass structured values into one ICU/localization message rather than stitching translated substrings in code;
- include translator context for ambiguous verbs/nouns, truncation, character limits, placeholders, markup, tone, and audience;
- do not reuse a key in a different grammatical context merely because the English text is identical;
- preserve placeholder names/types and document allowable formatting;
- keep markup out of translated strings where possible; when inline emphasis/links are unavoidable, use explicit placeholder boundaries rather than positional string splitting;
- do not assemble plurals with `if count == 1`; use locale plural categories including zero/two/few/many where relevant;
- do not infer gender/grammatical agreement from names, avatars, or binary user settings;
- keep brand/product names stable only when intentionally untranslated; transliteration is a locale decision, not automatic romanization;
- test empty, zero, one, two/few/many, large-number, negative, and unknown-value cases.

A message is not localization-ready if translators cannot see the whole sentence or cannot reorder all meaningful parts.

## Pseudolocalization workflow

Use pseudolocalization early and repeatedly, not as a final screenshot trick:

1. **Enable a controlled pseudo-locale** or deterministic transform in the development environment.
2. **Accenter visible Latin letters** to expose hard-coded/non-localized strings and encoding failure without making text unreadable to developers.
3. **Add visible boundaries** such as brackets so truncation/clipping is obvious.
4. **Expand representative strings** aggressively enough to expose fixed widths, missing wrapping, and overlap; do not treat one percentage as universal.
5. **Exercise placeholders/plurals** with zero/one/other and long variable values rather than only static copy.
6. **Run an RTL pseudo-direction pass** where supported to expose physical layout properties, missing isolation, bad mirroring, and punctuation placement.
7. **Inspect input paths** including paste, IME composition, validation errors, autocomplete, and bidi isolation.
8. **Record what pseudolocalization cannot validate:** real translation quality, correct cultural tone, shaping correctness in every font, native-speaker comprehension, and locale-specific legal wording.

Any untransformed visible string is a hard-coded-string candidate. Any clipped boundary marker is a layout defect. Do not hide failures by truncating all text or reducing minimum target sizes.
