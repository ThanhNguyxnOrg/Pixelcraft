# Streamlit

Evidence: current docs confirm `[theme]` keys including `primaryColor`, `backgroundColor`, `secondaryBackgroundColor`, `textColor`, `linkColor`, chart color arrays, `fontFaces`, `baseFontSize`, and light/dark/sidebar sections.

## Token mapping

Use `.streamlit/config.toml` first:

```toml
[theme]
base = "light"
primaryColor = "#0074ca"
backgroundColor = "#faf8f1"
textColor = "#161b24"
```

Map semantic tokens deliberately; primary color alone is not a design system. Use supported sidebar/light/dark tables and stable custom CSS only for gaps the config cannot express.

## Layout and responsive idioms

Use `st.columns`, containers, sidebar, tabs/expander/dialog/form intentionally. Streamlit layout is document-flow centric, not arbitrary CSS positioning. Avoid wide fixed grids and nested columns that collapse badly. Use `use_container_width` only where content benefits.

## Typography/custom fonts

`fontFaces`/base font settings are supported within documented constraints; complex type control is limited. Do not load heavyweight custom CSS/fonts just to imitate a web product if hierarchy/copy/layout can carry the direction.

## Motion/reduced motion

Streamlit provides little direct animation control. Use progress/spinner/status semantics honestly and avoid custom animated CSS that ignores reduced-motion. Long computation belongs in explicit status/progress patterns.

## Accessibility specifics

Use labels/help text, semantic ordering, meaningful chart titles/alt/summary, keyboard-focusable native widgets, and concise status announcements where supported. Custom HTML/components must preserve DOM semantics. Streamlit accessibility constraints are framework-dependent—verify rather than assuming full control.

## States idiom

Every input change can rerun script execution. Initialize `st.session_state` explicitly, use stable keys, cache expensive data with correct scope/invalidation, and isolate mutation. Use `st.form` to batch inputs when intermediate reruns are wrong. Render empty data, exceptions, permission/upload failure, missing secrets, stale cache, and long-running progress explicitly.

## Forms idiom

`st.form` batches widget state until submit. Use labels/help/placeholders correctly (labels are not optional), input validation after submit, preserve invalid values through session state/defaults, and never silently discard uploads.

## Do/don't pairs

| Do | Don't |
|---|---|
| `with st.form("batch"): ... st.form_submit_button("Review batch")` | rerunning expensive inference on every keystroke |
| explicit `st.session_state.setdefault("draft", "")` | relying on widget key side effects you never inspected |
| cache data with clear invalidation | per-user mutable data hidden in global cache |
| theme config plus restrained scoped CSS | selectors targeting unstable autogenerated DOM classes |
| `st.empty()/st.status` used for meaningful lifecycle | fake progress or spinner-only long tasks |

## Known traps

Script reruns, duplicate widget IDs/keys, stale cache, secrets leakage, session concurrency, unstable DOM selectors, sidebar overload, wide-mode false assumptions, uploaded file lifecycle, heavy objects reconstructed per rerun.

## Verification commands

```sh
streamlit run app.py
python -m pytest
python -m compileall .
```

Browser inspection can validate DOM/visual behavior only when the app is actually run. Playwright/browser tests are rendered evidence; Python unit tests are state/static evidence.
