# Gradio

Evidence: current docs confirm `gr.Blocks(theme=gr.themes.Soft())`, prebuilt themes, `.set()` for theme CSS variables, `css=` on Blocks, and stable `elem_id`/`elem_classes` escape hatches.

## Token mapping

Prefer themes before CSS:

```python
theme = gr.themes.Default(primary_hue="blue").set(
    loader_color="#0074ca",
)
with gr.Blocks(theme=theme, css=".gradio-container { }") as demo:
    ...
```

Map semantic tokens through documented theme variables first. Use `elem_classes` for stable hooks; autogenerated DOM selectors are brittle across versions.

## Layout and responsive idioms

Use Blocks rows/columns/tabs/groups/accordion according to task flow. ML demos often need input → control → output scan clarity, not dashboard chrome. Control density depends on expert frequency. Mobile embedding and narrow iframe behavior must be checked.

## Typography/custom fonts

Theme typography control is limited but theme objects/CSS variables can affect major surfaces. Use custom fonts only when licensing/loading/fallback are explicit; ML demo clarity usually matters more than decorative type.

## Motion/reduced motion

Gradio loading/progress semantics matter more than decorative motion. Use generator progress updates truthfully where supported. Custom CSS/JS animation must honor reduced motion and not interfere with streamed output.

## Accessibility specifics

Use component labels/info/placeholders appropriately, meaningful input/output ordering, text alternatives for media, visible focus in custom CSS, and keyboard inspection. Gradio component accessibility varies by component/version; custom components must not regress semantics.

## States idiom

Model queued/running/streaming/cancelled/error/empty states. Event handlers need concurrency/queue/cancellation semantics considered. Render missing model/file/input validation errors and preserve user input. Do not leave output blank when no result exists.

## Forms idiom

Input components are often live controls rather than a single submit form. Make computation triggers explicit when cost is high. Validate format/range/file type before expensive work and preserve failed inputs.

## Do/don't pairs

| Do | Don't |
|---|---|
| stable `elem_classes=["result-panel"]` hook | scraping generated class names in custom CSS |
| explicit Run/Generate button for costly work | inference on every slider movement without control |
| truthful queue/progress state | fake progress that never reflects backend work |
| input/output grouping by task flow | copying generic SaaS dashboard cards around everything |
| clear empty/error output text | leaving blank media/output after failure |

## Known traps

DOM instability across versions, queue concurrency, generator cancellation, large media memory/upload limits, hidden session leakage, theme variable sprawl, iframe embedding, mobile clipping, custom JS security/file access restrictions.
